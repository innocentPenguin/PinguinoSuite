## (a) Artist-exact ban by Spotify artist id
Problem: `!banartist` and Master "ban artist" append the artist NAME to `blocklist` (engine.py:820-830, 984-990). `blocked_reason` (rules.py:108) matches any word inside `name | artists`, so banning "Queen" also blocks "Queensryche" and a song titled "Queen of Hearts"; banning "Drake" misses an artist spelled differently by Spotify.
- Data already there: `norm_track` carries `artist_ids` (spotify_api.py:281) for every track; no extra API call.
- Settings (config_schema.py, group Rules): new list `blocked_artists`, one line per entry `"<artist_id>|<name>"` (name only for display and for the "unban by name" lookup). The existing `blocklist` keeps words and track ids.
- Matching: in `blocked_reason` (rules.py) after the track-id test: any `track["artist_ids"]` in the id set -> reason `artist:<name>`. Id match only; a ban by artist never uses substring on names. A feature credit counts (a banned artist as second artist still blocks, as streamers expect); `!banartist` bans only the FIRST artist of the playing song (as today), `!banartist <number>` (new, optional) picks the n-th credit.
- `!banartist`, Master `ban_artist`, `/api/block` kind=artist: write `blocked_artists` entry (dedupe by id), `_reject(..., "blocked")`, skip. If the song has no `artist_ids` (local file) fall back to the old name entry in `blocklist` and say so in the reply (`artist_blocked` message unchanged).
- `!unbanartist <name>` removes by name (case-insensitive, matches the stored name) or by id; empty argument = last rejected song's first artist, as now (engine.py:836). `!pardon artist` unchanged.
- Migration (once, in `Engine.__init__` after settings load, only when `blocked_artists_migrated` is not set in config.json): none of the old name bans can be mapped to an id offline, so they are KEPT as words (no behaviour loss); each time such a name is seen on a played/rejected track whose first artist name equals the entry exactly (case-insensitive), the engine adds the id entry and removes the word entry ("lazy upgrade"). Setup tab lists words and artists in two boxes so Ivan can see which are still words.
- Site blocklist (`site_block["artists"]`, engine.py:104): the site may send names or ids; ids matching `^[A-Za-z0-9]{22}$` go to the id set, the rest stay words.
- Autoskip (`_should_autoskip`, engine.py:~335) uses the same function, no change.
- Tests: unit: id ban blocks a collab track but not "Queensryche"; word "queen" still blocks both (documented difference); lazy upgrade; unban by name and id; local file fallback; site ids. e2e: `!banartist` then a request of another song of the same artist is refused with `blocked`.

## (b) Now-playing announce per tier
Today: one switch `announce_track_on` + one template `announce_track` (config_schema.py:70,154); `_track_changed` (engine.py:305) queues `{seq, ts, text}` and the Host polls `/api/announcements`.
- Proposal: the tier of the item that starts is known (`self.now_item["tier"]`: 0 normal, 1 sub, 1.1/1.2 tier 2/3, 2 redeem; source streamer/fallback has none). Add settings `announce_tiers` (list of `"normal"|"sub"|"redeem"|"streamer"|"fallback"`, default `["normal","sub","redeem"]` so playlist/fallback songs are not announced and chat is not spammed) and three optional templates `announce_track_sub`, `announce_track_redeem` (empty = use `announce_track`). Placeholders as now plus `{tier}` (name) and `{requester}`. No new switch; `announce_track_on` stays the master.
- Rate guard: `announce_min_gap_s` (default 20): if songs change faster (skipping), drop the older line instead of queueing, so the Host never posts a burst.
- Host fields: each line becomes `{seq, ts, text, kind:"track", tier:"normal|sub|redeem|streamer|fallback", requester, uri}` (additive, v1 readers ignore the new keys). The Host stays dumb: it posts `text`; `kind` lets the Host route other announcement types later (queue opened/closed, banned song) with its own on/off. Duplicates: lines carry `seq`, the Host remembers the last posted seq, and the module never posts to chat itself (hard rule). `uri` lets the Host de-duplicate the same song announced twice within 60 s.
- Tests: tier mapping for each source, `announce_tiers` filter, template fallback, min-gap drop, seq monotonic, lines older than 120 s dropped (existing), field presence on the endpoint (also in `SPOTIFY_CONTRACT.md`).

## (c) Request leaderboard: week / month / lifetime
Today `board = {"requesters": {name: n}, "songs": {id: {plays, skips,...}}}` (engine.py:64, `_board_add` :262, `leaderboard` :272): all-time only, names as keys, songs pruned to 3000. `GET /api/leaderboard?limit=` returns all-time requesters, most played, most skipped. Ivan decided: the request leaderboard lives ONLY on the song pages (not the site's main boards), so it stays in this module and is not sent through Host\HostPeriods (Docs\BOARDS_PERIODS.md has the Host's boards; no data goes there).
- What week/month needs: per-day buckets. `board["days"] = {"2026-10-23": {"requesters": {name: n}, "plays": {songkey: n}, "skips": {songkey: n}}}`, key = local date in America/Chicago (same zone as the Host periods; one helper), kept for 400 days (older days are folded into `board["archive_months"]["2026-09"]` the same shape, then dropped after 24 months), plus the existing all-time totals untouched (migration: nothing to do, old data stays "all time"; week/month start empty the day this ships, which the page should say: "since <date>").
- API: `GET /api/leaderboard?period=day|week|month|all&limit=` (default `all` = unchanged output, so the current page keeps working). Week = ISO week of today in Chicago, month = calendar month. Response adds `period`, `key` (e.g. `2026-W43`), `since` (first day with data), and the same three lists; names are lower-cased keys with the display name stored once in `board["names"]` (fixes "Ivan"/"ivan" splitting).
- Cost: a day bucket is a few KB; computing a week = merge of 7 dicts on demand, cached for 30 s. state.json stays small because plays/skips per day store only song keys with counts and titles come from `board["songs"]`.
- Privacy: names only (as today); `!rankme`-style per-user command not planned. Banned users (`blocked_users`) are hidden from the lists.
- Tests: bucket rollover at local midnight (injectable clock), ISO week boundary (Mon), month boundary, `period=all` equals old output, prune and fold, case-merging of names, hidden blocked users.

## (d) `POST /api/mod-action {action:"lyrics_toggle"}` for the Master View (20 - Suite)
- Server: `p_mod_action` (server.py:512) passes any action to `Engine.mod_action` (engine.py:968) which today starts with "needs a current song" (returns `none` if nothing plays). `lyrics_toggle` is a settings action: handle it BEFORE the `t` check: `save_settings({"lyrics_on": not settings["lyrics_on"]})`, `_bump()`, return `{"ok": true, "code": "lyrics_on"|"lyrics_off", "lyrics_on": bool}`. Optional body `value: true|false` sets instead of toggling (idempotent when the button is clicked twice or two Master Views are open).
- Same auth as the other mod actions (`app_ui` origin check, server.py:129); no new endpoint. `GET /api/state`-like info for the button's state: `/api/now` and `/api/lyrics` already exist; add `lyrics_on` to the `engine.now_info()` dict so the Master View can show the current state without a second call.
- Overlay: `/overlay/lyrics` already goes blank when `lyrics_on` is false (engine.py:1225); toggling on while a song plays shows lines at once (the lookup is cached, see audit 4 for the negative-cache fix).
- Tests: toggle twice returns on/off alternately; explicit `value` is idempotent; works with nothing playing; unknown actions still raise QueueError -> 400; settings persisted.
- Tell 20 - Suite: button label "Lyrics: on/off", reads `lyrics_on` from `/api/now`, posts `{action:"lyrics_toggle"}`.
